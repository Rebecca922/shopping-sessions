# Shopping Sessions 第一版：怎样从题目推导出程序

这是一份可编译的 C++ 计算实现，配合 Python / PyArrow 将最终结果写成 Parquet。
学习时先读本文，再看 `src/main.cpp`。不需要先理解全部代码。

## 当前完成到哪里

- C++ 计算结果与官方 36 个手写边界样例全部一致。
- 30 组随机脏数据，与独立 Python 慢速参考实现的两张表全部一致。
- 全空数据在 1、3、8 线程下都正确产生空结果。
- 当前执行环境没有 Docker，也不能下载 PyArrow 或 Rust；尚未执行官方 100 万事件 dev 数据、Parquet 端到端检查、Docker 容器检查、2000 万 / 6000 万事件性能测试。
- 因此这是“计算层已验证的第一版”，不是已经通过官方提交或测出竞争成绩的版本。小样例用时不能与榜单比较。

## 1. 题目实际要做什么

网店给你浏览、购物车、购买、广告点击和账号关联记录。
输出两张表：每人每天的访问和购买情况，以及每个广告每天的归因和助攻情况。

“同一个人”由 links 文件明确提供的关系决定，不能靠相似名字、相似时间或相似行为猜。
“广告导致访问”在现实中需要因果证据；这道题不要求证明因果，而是要求遵循固定记账规则：访问开始前七天内最后一次有效点击获得归因。

有效事件不会因为夹在一次访问中间就被删除。它们都计入事件数；会话划分只是给事件分组。

## 2. 为什么不是直接读一遍就结束

输入经过打乱。一开始读到的记录，不一定是时间上最早的记录。

例如，先读到 10:00 和 11:00 的事件，会觉得它们隔了 60 分钟，是两次访问。
但最后一个文件里可能还有 10:30 的事件：两个间隔恰好都是 30 分钟，实际只有一次访问。
所以不能在第一次看见 11:00 时就最终确定会话数。

重复记录也有类似问题：晚读到的副本可能入库更早，必须替换先读到的版本。
这意味着必须保留状态、重新访问状态，或先整理顺序。

单次读入不等于总共只处理一次。流式系统也需要保存状态，并在后续信息到来时更新。

### 怎样理解 O(N)

O(N) 表示数据量翻倍时，工作量大致也翻倍。这里讨论的是增长速度。

- 扫三遍：大约 3N 次工作，仍是 O(N)。
- 扫一遍：大约 N 次工作，也是 O(N)，实际常数更小。
- 每个事件都重新检查所有事件：可能是 N×N，即 O(N²)。
- 常规比较排序通常为 O(N log N)。

因此“清洗一次、统计一次、写出一次”不代表算法差。真正要避免的是重复搜索和过大的中间结果。

## 3. 为什么选 C++，Python 又负责什么

选择 C++ 的原因是：你学过它，而本题需要逐条检查大量记录，并控制中间记录的空间。
编译器会把核心循环提前编译为机器指令；紧凑的数据结构也有助于减少内存流量。

这不等于 Python 数据工具一定慢。DuckDB、Polars、PyArrow 的核心操作也由编译代码执行。
这版把自定义规则和算法放在 C++，把已有可靠库擅长的 Parquet 编码交给 PyArrow。
Python 不逐个计算事件、会话或广告助攻。

这个选择也有代价：自写解析器和并行代码需要更多验证。后面应根据正式测量决定优化方向。
PyArrow 导入、结果转换、中间文件读写都会计入比赛时间，尚未证明这些成本足够低。

## 4. 算法选择，逐项说明

### A. 读取和解析

内存映射 mmap 可以让程序通过内存地址访问文件内容，避免先把整个文件复制到一个字符串。
这不是“不占内存”或“不需要磁盘读取”：访问的页面仍要读取，并受到内存限制和操作系统缓存影响。

大文件按约 2 MB 的完整行区块切成任务，由多个线程领取；这样不会让一个线程独自处理最大的文件。
各线程主要写自己的缓存，避免每条记录都争抢同一个容器。

CSV 严格按 rules.md 解析，不自动去空格，不把 CR 当换行，不修复非法引号。
只有文件第一行作为标题跳过，正文中与标题一样的行不被无条件跳过。

### B. 时间和价格

时间统一为整数毫秒，之后只做整数比较。
F1 / F2 严格验证日历和时区；F3 只接受 ASCII 数字，允许前导零，检查溢出和窗口。
特别大的 F3 直接认定不在窗口内，不允许溢出成一个看起来合法的时间。
金额用整数“分”，避免浮点误差；view / cart 不检查价格。

### C. 身份合并：并查集

并查集维护“哪些 ID 属于同一组”。读到 a,b 就连接它们的组。
如果 a 连着 b，b 连着 c，即使 a,c 没直接出现，也属于同一组。

采用按大小合并和路径压缩，避免几百层链导致每次查找都走几百步。
组内另外维护字节序最小的名字，不强求内部代表节点就是那个名字。
内部用于快速查找的编号，与最后输出的人名是两件不同的事。

### D. 事件去重：按 event_id 分桶的哈希表

哈希表可以理解为用 ID 快速查记录的字典。
相同事件 ID 一定进入相同的去重桶，在桶内保留 ingest_ts 最小的记录。
哈希只是定位工具，遇到哈希相同仍比较原始字符串，因此不会把哈希碰撞当成同一个事件。

特别注意：重复副本可能写着不同用户，所以不能先按用户拆开、再各自去重。

代码在解析时提前算出有效性，减少以后再读字段的次数，但无效副本仍进入去重表。
例如，最早副本无效、后来副本有效，去重后仍选最早的无效副本，然后删除事件。
因此这是提前计算检查结果，没有改变题目要求的逻辑顺序。

### E. 排序和会话：按人分桶、桶内按人和时间排序

通过去重的事件再按人的内部编号分桶。
同一个人的所有 ID 此时已经映射到同一个编号，所以会进入同一个桶。
每个桶用 std::sort 排序，先比较人，再比较毫秒时间。

这是第一版最主要的 O(N log N) 部分，未声称整个算法已经是 O(N)。
以后可以考虑对整数键做基数排序，即分段按数字位归类，但是否更快需要测量。

排好后顺序扫描，相邻有效事件间隔大于 30 分钟就开始新会话。
每个事件都参与会话的计数；跨午夜也记在会话开始那一天。
同一次扫描中累计每日事件数、收入和类别金额，减少另建事件级中间表。

### F. 广告归因：从早到晚移动位置

点击按人、时间、click_id 字节序排列。
会话从早到晚前进时，点击位置也只向前移动，记录“已经看过的、时间最新的点击”。
会话开始时如果最近点击不超过七天，就归给它，否则归 organic。
同一时间先遇到字节序最小的 click_id，保留它，不被后面的同时间点击覆盖。

从早到晚比较自然，是因为看到会话开始时，可以确定哪些广告已经发生。
从晚到早也能设计正确算法，但不能只是把循环反过来就得到相同结果。

### G. 广告助攻：把一次点击看成七天的影响区间

发生在 t 的点击，能够助攻所有开始于 [t, t+7天] 的会话。

同一广告在 09:00 和 10:00 各被点击一次，两个七天影响区间大量重叠。
重叠部分里的同一个会话，仍只能给这个广告记一次助攻。

代码用左右两个位置找出各点击覆盖的会话下标范围。
再为每个广告记录已经覆盖到哪里，只计算新覆盖的部分。这等价于把重叠区间取并集。
新覆盖部分按会话开始日期分段，只增加每日计数，不生成庞大的“点击 × 会话”连接表。

这里再次用到了你的“一边走一边记录”想法：时间有序后，左右边界都只向前走。

### H. 输出

C++ 写出紧凑的二进制统计行和字符串字典。
Python 按批读入这些统计行，使用 PyArrow 输出 Parquet。
日期明确写成 DATE，没购买时 top_category 写成 null，助攻但没归因的广告也保留一行。

## 6. 本地先跑哪一步

在解压后的 shopping-sessions 目录中执行。

### 仅检查 C++ 计算，无第三方 Python 依赖

需要 C++20 编译器、Python 3。Mac 安装过 Xcode Command Line Tools 后通常能用 clang++。

```sh
make core
make binary-fixtures
python3 scripts/random_check.py 30
```

如果默认编译器不合适：`make core CXX=clang++`。
程序使用 Linux / macOS 都支持的 mmap，但归档中不含平台相关的预编译程序。

### 检查实际 Parquet 输出

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
pip install 'polars>=1.30,<2'
make fixtures
```

### Docker 中按比赛限制检查

先启动 Docker Desktop。这里默认构建比赛要求的 linux/amd64。

```sh
make container-fixtures
make dev
make run-dev
```

把已下载的官方 dev-answer.zip 解压到本目录，形成 dev-answer/user_daily.csv 等文件，然后：

```sh
make check-dev
```

Apple Silicon 上默认 amd64 使用模拟，时间不能代表比赛机器。
可以用 `make container-fixtures PLATFORM=linux/arm64` 快速本地检查；提交前仍要验证 amd64。

只有真实 Parquet 检查、官方 dev 检查和容器运行都通过后，才应称为可提交的已验证版本。

## 7. 怎样继续优化，而不是盲目换语言

核心程序每个阶段都向 stderr 打印累计耗时。
当前哈希表和排序在内存中完成，没有实现内存不足时的磁盘排序；最终规模下是否满足 24 GB，需要实测，不能由小样例推出。
先在正式规模上比较解析、去重、排序统计和最终 Parquet 编码的耗时。
再决定是否改进排序、减少中间文件、直接在 C++ 写 Parquet，或调整并行任务。
任何优化都要先保持 36 个边界样例和完整 dev 输出一致。

仓库里可以保留源码和小型官方边界样例；不要提交 dev 原始数据、编译产物和临时输出。
顶层 Dockerfile 是评测入口；整个程序退出才停止计时。
